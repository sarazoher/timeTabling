# Multilingual (Hebrew/English) implementation — notes

Notes for anyone/me working on this project next. 
Explains what was added for Hebrew/English support, 
what broke along the way, and why things were done a certain way — so nothing gets accidentally undone later.

- `timetable_frontend/course_translations.json` — English versions of course names, lecturer names, and prerequisites.
- `timetable_frontend/translations/en/LC_MESSAGES/messages.po` and `.mo` — English translations of the UI text.
- `timetable_frontend/translations/he/LC_MESSAGES/messages.po` and `.mo` — Hebrew translations of the UI text.

- `requirements.txt` and `timetable_frontend/requirements.txt` — added `Flask-Babel`.

## 1. Two separate kinds of translation

- **The app's own text** (buttons, labels, error messages) — this is fixed text
  that lives in the code. Handled with Flask-Babel, a standard Flask tool for
  this.
- **The timetable's content** (course names, lecturer names, prerequisites) —
  this comes from your Excel file and changes whenever the Excel changes. It's
  handled separately, with its own translation file.

These are kept apart on purpose. The app's text is fixed and known ahead of
time. The Excel content isn't — it changes any time someone edits the file.

## 2. The app's own text (Flask-Babel)

In `timetable_frontend/app.py`:
- The site defaults to Hebrew. The chosen language is remembered in the
  browser (more on that in section 6).
- Visiting `/language/en` or `/language/he` switches the language.
- Every piece of visible text in `app.py` and the templates is wrapped in a
  `_(...)` function call. That's what marks it as "this needs a translation."

The translations themselves live in
`timetable_frontend/translations/en/LC_MESSAGES/` and `.../he/LC_MESSAGES/`,
as `.po` files (human-editable) and `.mo` files (the compiled version the app
actually reads).

**One detail worth knowing:** in the code, every `_(...)` call uses the
**English** text, like this:

```python
raise ValueError(_("The number of years in the degree must be between 1 and 10."))
```

and the Hebrew file translates that English text into Hebrew. This might seem
backwards, since the original app was all Hebrew. The reason: if a translation
is ever missing or a translation file breaks, the tool falls back to showing
whatever text is in the code — the English version. That's an easier problem to
notice and fix than the alternative (a broken English-locale page silently
showing Hebrew instead). This was a deliberate choice, not an accident.

**If you add new text to the app**, here's how to translate it:
```bash
cd timetable_frontend
pybabel extract -F babel.cfg -o messages.pot .
pybabel update -i messages.pot -d translations
# now edit the .po files to add the missing translations
pybabel compile -d translations
```
That last step matters — the app reads the compiled `.mo` files, not the `.po`
files directly. Editing a `.po` file alone does nothing until you compile it.

## 3. Timetable content (course names, lecturers, prerequisites)

`timetable_frontend/course_translations.json` holds the English version of
each course, matched up by **course ID** (a number), for example:
```json
"8500012": {
  "name": "Data Structures",
  "lecturer": "Dr. Nur Igor",
  "prerequisites": "Discrete Mathematics + Introduction to Computer Science in C++"
}
```
When someone views the timetable in English, the app looks up each course by
its ID in this file and swaps in the English text. In Hebrew, this file isn't
used at all — the original Excel data is shown as-is.

It's matched by course ID rather than by name because, as it turns out, names
in the Excel file aren't always spelled consistently (see next section) — an
ID is the one thing guaranteed not to change.

**Important:** this file was built by hand, once, based on the Excel file at
the time. It doesn't update itself. If you add a new course to the Excel file
later, it won't have an English translation until someone adds one here.

## 4. A real bug found while translating: inconsistent lecturer names

While filling in `course_translations.json`, three lecturers turned out to be
listed under two different spellings each, depending on the row:

- `ד"ר ויסבלט טל` and `ד"ר טל ויסבלט` — same person, name written in a different order
- `ד"ר כרמון מרים שיראל` and `ד"ר מרים כרמון` — same person, one row is missing part of the name
- `מר גרין עוזרי נתנאל` and `נתנאל עוזרי` — same person, one row is missing part of the name

These were confirmed with the project owner before changing anything, since
guessing wrong about a real person's name is worse than leaving it alone.

**Why this mattered more than expected:** the scheduler (`timetable_backend/scheduler.py`)
prevents a lecturer from being booked for two overlapping classes — but it does
this by comparing the lecturer's name as an exact piece of text. Since these
three people were spelled two different ways, the scheduler thought they were
six different people, not three. That means it could have accidentally
double-booked one of them. It happened not to, in the schedule that existed at
the time — but only by luck, not because the system prevented it.

**What was fixed:**
1. Picked one correct spelling for each of the three lecturers (the fuller
   name, so nothing gets accidentally left out).
2. Corrected the spelling directly in `courses.xlsx`.
3. Re-ran the scheduler to rebuild `courses.json`, `timetable.json`, and the
   matching `.xlsx` files from the corrected data.
4. Checked that there are no more scheduling conflicts, and updated
   `course_translations.json` so each lecturer's English name is now spelled
   the same way everywhere.

**Good habit going forward:** if you ever add or edit a lecturer's name in the
Excel file, make sure it's spelled *exactly* the same everywhere that person
appears. The system doesn't catch near-matches — a typo creates what looks like
a brand-new, different lecturer.

**Still unresolved:** courses `8500032` and `8500035` have almost the same name
("Applied Project in Artificial Intelligence," one with a trailing period),
same lecturer, same prerequisite — but different credit amounts (4.0 vs 4.5).
Not yet confirmed whether these are two real, separate course options, or a
leftover duplicate that should be removed.

## 5. Right-to-left / left-to-right layout

The calendar grid was already built in a way that didn't depend on page
direction — lucky, since it meant switching to English didn't break the
layout. A few specific pieces of styling did need fixing for English, though,
since they were hardcoded for Hebrew:
- the day-of-week headers,
- the colored side-border on each course card (was always on the right, which
  looks wrong once the page reads left to right),
- the same border on the small course cards in the "all semesters" view.

These fixes are in `timetable_frontend/static/calendar.css`, near the bottom,
under a comment marking them as language-direction overrides. Some older,
unused styles in that file (`.compact-*`, `.overview-*`, `.compressed-*`) were
left untouched since nothing currently on the page uses them.

## 6. The language choice is remembered across restarts

The chosen language is stored in the browser (a cookie), not on the server.
This was checked and works as intended: pick a language once, and it stays
picked — even if you close the app and reopen it later. You don't need to
re-select your language every time.

(There was a brief detour where this was changed to reset to Hebrew on every
restart, then reverted, because "pick once and it stays" is simply the better
experience for a tool one person uses regularly.)

One small thing to know: the cookie is protected by a fixed password-like value
in the code (`app.secret_key` in `app.py`). That's perfectly fine as long as
this app only runs on your own computer, which is how it's built to run today.
If this app is ever put on a shared server or made accessible to other people
over a network, that fixed value should be replaced with something private and
not stored in the code.

## 7. Things to keep in mind for later

- **If you add an Excel-upload feature**, `course_translations.json` won't
  automatically stay in sync. A newly added course will show up in Hebrew even
  in English mode until someone manually adds it to the file. A changed
  lecturer name on an existing course will keep showing the *old* English
  translation until it's updated by hand. Worth adding a simple check that
  warns when a course in the timetable has no matching entry in this file.
- **Nothing in the system catches near-matches or typos** — not in the
  scheduler's lecturer-conflict check, not in the translation lookups. Spelling
  matters exactly.
- The duplicate-looking AI project course (`8500032` / `8500035`, section 4)
  is still an open question.
